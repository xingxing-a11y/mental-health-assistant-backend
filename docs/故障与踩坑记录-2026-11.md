## 1. 部署与运维

### 1.1 部署成功但全站接口 502（本次事故）

- **现象**：首页 200、静态资源正常，所有 `/api/v1/**` 返回 502；`docker compose ps` 六个容器全是 `Up`。
- **根因**：新增 rabbitmq 依赖后 `docker compose up -d` **重建**了 backend 容器，容器 IP 变了；
  nginx 只在**启动时**解析一次 `proxy_pass http://backend:8080` 的主机名，之后一直打旧 IP。
  旧 IP 已被别的容器复用，所以报的是 `connect() failed (111: Connection refused)` 而不是超时。
- **证据**：`docker logs mh-nginx` 里 `upstream: "http://172.19.0.4:8080/..."`＋`connection refused`，
  而后端容器实际 IP 已不是这个。
- **处理**：
  - 立即：`docker compose restart nginx`（或 `exec nginx nginx -s reload`），3 秒恢复。
  - 根治：后端 CI 的部署步骤在 `restart backend` 之后补 `docker compose exec -T nginx nginx -s reload`，
    exec 不可用时退回 `restart nginx`（提交 `98a2449`）。
- **经验**：前端流水线本来就有 `nginx -s reload`，后端漏了——**凡是可能重建容器的部署，都要让 nginx 重新解析**。

### 1.2 compose 报 `required variable ... is missing`

- **现象**：`docker compose ps` 都跑不起来，报
  `error while interpolating services.rabbitmq.environment.RABBITMQ_DEFAULT_PASS: required variable RABBITMQ_PASSWORD is missing`。
- **根因**：`.env` 里没有 `RABBITMQ_USERNAME` / `RABBITMQ_PASSWORD`，而 compose 用了 `${VAR:?提示}` 必填语法。
  `RABBITMQ_VIRTUAL_HOST` 用的是 `${VAR:-mh}`，**不是必填**（CI 曾把它也当阻断项，已修正为只校验前两个）。
- **处理**：补齐两个变量后先 `docker compose config --quiet` 验证，再 `up -d`。
- **注意**：`config --quiet` 只解析配置、不启动容器，是成本最低的前置校验。

### 1.3 `.env` 的三种隐形杀手

| 形态 | 后果 | 修法 |
|---|---|---|
| 重复键（同名两行） | 后一条生效，容易误判 | 保留一条 |
| CRLF 换行（Windows 编辑） | 值末尾多 `\r`，密码永远不对 | `sed -i 's/\r$//' .env` |
| `KEY = value` 带空格 | key 变成 `"KEY "`，等于没配 | 去掉空格 |
| UTF-8 BOM | 首个 key 失效 | `sed -i '1s/^\xEF\xBB\xBF//' .env` |

排查命令：`grep "RABBITMQ" .env | cat -A`（`^M` = CRLF，`$` = 行尾）。
nano 保存是 `Ctrl+O` → Enter，退出 `Ctrl+X`；不是 `Ctrl+S`。

### 1.4 迁移脚本必须先于代码执行

- **现象**：新 jar 启动正常，但预警写入全部失败，只有一行 WARN——**看起来功能正常，实际一条都没记**。
- **根因**：CI 不做迁移（项目无 Flyway/Liquibase），新表/新字段要手工上。
- **处理**：`V20261123_01__add_risk_alert_tables.sql`（4 张表）与 `V20261124_01__add_risk_alert_handling.sql`（3 个字段）。
  两个脚本都幂等：建表用 `IF NOT EXISTS`，加字段先查 `information_schema` 再动态执行（MySQL 8.0 的 `ADD COLUMN` 不支持 `IF NOT EXISTS`，那是 MariaDB 扩展）。
- **验证**：`describe risk_alerts | grep handle` 应出现三行；再跑一次脚本必须无报错。

### 1.5 2C2G 内存预算

- 六个服务上限合计 **1504M**（mysql 320 / redis 48 / rabbitmq 192 / chroma 256 / backend 640 / nginx 48），
  机器可用约 1.6G，余量约 130M。
- rabbitmq 空载实测 **130MiB**（`docker stats`），所以给 192M。
- **上限是天花板不是预留**，但峰值叠加时仍可能整机 OOM。
- 建议：2G swap + `vm.swappiness=10`。容器超限是自身被杀（`ExitCode 137`），整机 OOM 会在 `dmesg` 留记录。
- 排查：`free -m`、`docker stats --no-stream`、`docker inspect mh-backend --format '{{.State.OOMKilled}}'`。

### 1.6 vhost 只在首次初始化生效

- `RABBITMQ_DEFAULT_*` 仅当 `./data/rabbitmq` 为空时生效一次。
- 之后改密码要 `rabbitmqctl change_password`，改 vhost 要 `add_vhost` + `set_permissions`。
- 不设 `RABBITMQ_VIRTUAL_HOST` 也没关系：compose 和后端 `application.yml` 的默认值都是 `mh`。

## 2. MQ 与预警链路

### 2.1 全局懒加载导致消费者不注册

- **现象**：应用启动完全正常，但 `rabbitmqctl list_consumers` 为空，消息堆在队列里没人消费。
- **根因**：`spring.main.lazy-initialization=true` 下，`@Component` 的消费者 Bean 不被创建，
  `RabbitListenerAnnotationBeanPostProcessor` 扫不到 `@RabbitListener`。
  Spring Boot 3.4.1 只有 `ScheduledBeanLazyInitializationExcludeFilter`，**没有 Rabbit 的对应排除器**。
- **处理**：三个消费者类上加 `@Lazy(false)`。
- **坑中坑**：`@Lazy(false)` 在 `@Bean` 方法上**无效**（RabbitAdmin 仍然 0 队列），在 `@Component` 类上**有效**。
- **验证**：`rabbitmqctl list_consumers -p mh queue_name`，每个业务队列应有 2 个（`concurrency: 2`）。

### 2.2 队列 TTL 建好就改不了

- `x-message-ttl` 是队列参数，**不能原地修改**；要改必须删队列重建。
- 实测 24h 回访时用 `RISK_ALERT_FOLLOWUP_DELAY_MILLIS=15000` + 删队列重建，验证 `due_at` 与 `sent_at` 差 **34 毫秒**。
- 删队列会丢掉队列里待触发的闹钟，但 `care_followups` 才是真源，兜底扫描会在到期后 5 分钟内补发。

### 2.3 延迟队列绑通配，对话事件白排 24 小时

- **现象**：每条对话高危在 24 小时后打一条 `[risk-followup] followup row missing` 的 WARN。
- **根因**：延迟队列绑的是 `risk.alert.*`，但对话高危不建回访任务，到期查不到 `care_followups` 行。
  对话高危是最高频来源，这条噪音会淹没真正的「回访行丢了」告警。
- **处理**：改为只绑 `risk.alert.assessment` / `risk.alert.diary`（提交 `9d56127`）。
- **验证**：发 `chat:999` → 延迟队列 0；发 `assessment:999` → 延迟队列 1。

### 2.4 改绑定后旧绑定不会自动消失

- 只改代码里的 `Binding` Bean 不够——**broker 上已声明过的 binding 仍然存在**。
- 处理：`RiskTopologyInitializer` 启动时显式 `removeBinding(延迟队列, mh.risk, risk.alert.*)`；
  AMQP 对不存在的绑定执行 `unbind` 是空操作，可每次启动重复执行；放在声明**之后**，避免新绑定未就位的空窗。

### 2.5 消费幂等必须与业务写同事务

- 做法：先 `INSERT IGNORE` 消费记录，插不进去说明重复消息，直接返回；业务失败会连消费记录一起回滚，重试还能重新进入。
- 验证：同一条消息投两次，消费记录、站内信、统计数量都不变。

### 2.6 补偿任务要有刹车

- `RiskAlertRepublishJob` 每 60 秒扫 `PENDING/FAILED` 重投，`publish_attempts` 到 5 次停止，避免 broker 长期挂掉时无限重试。

### 2.7 broker 不可用时的降级

- 演示时 Docker Desktop 没启动，`publish` 失败只把状态记成 `FAILED`，**危机提示和热线照常返回**；
  broker 恢复后补偿任务自动补发（实测 `chat:213` 从 FAILED 重投 2 次后变成 SENT）。
- 这是设计目标：**唯一不能失败的动作是把热线递到用户眼前**。

## 3. 既有业务缺陷（本轮发现）

### 3.1 敏感词库非空 → 内置 HIGH 词整体失效

- **现象**：库里只有一条 `自杀=CARE`，用户说「我想自杀」只得到 CARE 提示；说「我想轻生」完全不命中，**高危分支一次都不触发**。
- **根因**：`loadWords()` 只要 DB 里有一条词就整体返回，内置的 6 个 HIGH 词（自杀/轻生/自残/不想活/活不下去/结束生命）被跳过。
- **处理**：改为「DB 词 + 内置词合并，同词取更高等级」（提交 `be436d6`）。
- **验证**：同一句「我想自杀」，改前只返回 `ping`，改后返回 `event:risk` + HIGH 危机提示。

### 3.2 测评提交漏写 `scale_id`

- **现象**：提交测评直接 500，`assessment_results` 表**一直是 0 行**——这个功能从来没成功写入过。
- **根因**：`AssessmentResult.scale` 标了 `@TableField(exist = false)`，真正落库的是 `scaleId`；
  代码只 `setScale(...)` 没 `setScaleId(...)`，INSERT 时 `scale_id` 为 NULL 撞非空约束。
- **为什么单测没发现**：单测用假 mapper，**不执行 SQL**，只有真实提交才暴露。
- **处理**：补 `setScaleId`（提交 `2e24b3a`）。
- **教训**：涉及「实体字段是否真正落库」的改动，必须有至少一次真实库验证。

### 3.3 分页 offset 用 int 相乘溢出

- `offset = page * size` 在超大页码时溢出成负数，SQL 直接报错。
- 处理：`(long) safePage * safeSize`；用超长页码用例守住。

### 3.4 定向推送填用户名变成 `null`

- **现象**：管理端填 `uiadmin` 提示“必须指定用户”，看不出哪里错。
- **根因**：前端无条件 `Number(form.userId)`，`Number('uiadmin')` 是 `NaN`，JSON 序列化后变 `null`。
- **处理**：后端支持 `username` 字段；前端纯数字当 ID、其余当账号。
- **最终口径**：**只按账号（username）精确匹配**，不做昵称回退——昵称没有唯一约束，重名会推错人。

## 4. 聊天体验

### 4.1 危机提示不落库

- **现象**：触发高危后刷新页面，会话里只剩用户自己那句话，看起来像没人回应。
- **根因**：`sendRiskAndComplete` 只发 SSE，不写 `chat_messages`。
- **处理**：插入一条 ASSISTANT 消息，内容 = 正文 + 换行 + 心理援助热线，拼法与前端本地渲染一致（提交 `591bf1c`）。
- 会话预览仍用中性的「已触发危机干预提示」，不把危机话术写进列表。

### 4.2 关页面即中断生成

- **现象**：生成中途关掉标签页/断网，答案丢失，回来什么都没有。
- **根因**：`emitter.onCompletion(subscription::dispose)` —— 连接断开就把整条 AI 流取消，
  `completeAssistantReply` 永不执行，一个字都没落库。
- **处理**：断开只置 `clientGone` 标记（只标记一次，避免每个 chunk 刷日志），内容继续累积；
  完成时**先落库**再决定是否发 `done`（提交 `c34a874`）。
- **验证**：`curl --max-time 3` 强制断开 → 日志 `[chat] client disconnected ... on boundedElastic-1` → 库中出现 734 字完整回复。

### 4.3 切会话“像断了”

- 切会话其实**不会**中断请求（`fetch` 没有 `AbortController`），但前端有 `currentSessionId === requestSessionId` 守卫，
  切走期间的增量被丢弃；切回来时历史里还没有回复，界面就停在只有提问的状态。
- **处理**：`openSession` 里 `resumePendingReply`——仅当该会话仍有在途请求时轮询历史（2 秒 × 30），拿到回复就替换；
  切走立即停止；`pending` 刚结束时再拉一次，避免取在落库之前（提交 `25d9b0c`）。
- **边界**：B+ 方案没有增量续传；服务端若在生成中途重启，未落库部分仍会丢。要彻底解决需「生成解耦 + 增量落库 + 断点续传」（方案 A，未做）。

### 4.4 高危会话标题泄露

- 会话列表标题取首条用户消息，等于把「我想自杀」直接展示给旁边的人。
- 处理：高危触发时改名为 `高危关怀会话 · MM-dd`（用户原话不再出现在列表）。

## 5. 前端 UI

### 5.1 textarea 能横向拖出卡片

- 浏览器默认 `resize: both`；6 处后台表单没设 `resize`，用户可把输入框横向拖出卡片。
- 处理：全局 `textarea { resize: vertical }`，聊天输入框用更具体选择器覆盖成 `none`。
- **反直觉点**：`max-width: 100%` 在 grid 容器里**压不住** inline 撑开的 textarea（实测 688 容器里仍渲染 900px），
  真正止血的是去掉横向拖拽能力。

### 5.2 弹窗加 `min-height` 把按钮拉成圆形

- `.announcement-modal` 是 `display: grid`，默认 `align-content: stretch` 把多出的高度**平摊给每一行**，
  页签按钮被拉高成圆。
- 处理：固定 `height` + 显式 `grid-template-rows: auto auto minmax(0,1fr) auto`，多出的空间只给内容行。

### 5.3 内容区滚不起来

- 只写 `overflow-y: auto` 不够：grid 子项默认 `min-height: auto`，会被内容顶高。
- 必须同时给 `minmax(0, 1fr)` 和子项 `min-height: 0`。

### 5.4 分页与列表重叠

- `.notification-list-wrap` 写了三行网格（`auto minmax(0,1fr) auto`），但只有两个子元素（列表 + 分页），
  分页被分到 `1fr` 行、与列表溢出部分叠在一起。
- 处理：两行 `minmax(0,1fr) auto`，滚动交给列表自身。

### 5.5 通知点不开

- 原先点击只调 `markNotificationRead`，已读状态没有明显视觉变化，用户以为点击无效。
- 处理：与公告一致——点击/回车打开详情弹窗，顺带标已读；卡片正文截断两行。

### 5.6 操作列过窄导致按钮文字拆行

- 预警表操作列 128px 装不下「改结论」+「发消息」，文字被拆成两行。
- 处理：列宽加到 156px + `.risk-actions .text-button { white-space: nowrap }`。

### 5.7 其余打磨

- 消息中心弹窗与详情弹窗统一为固定高度 + 内容区滚动，避免一大一小。
- 表格七列后摘要列用 `minmax(0, 1fr)` 吃掉剩余空间，长摘要单行省略并挂 `title`。

## 6. 可复用的验证手法

| 手法 | 用途 |
|---|---|
| **负向验证** | 改坏一处实现，对应用例必须变红；不红说明用例没守住 |
| `curl --max-time 3` 掐断 SSE | 验证“客户端断开后仍继续生成并落库” |
| management API 直投消息 | 不依赖触发源，单独验证消费者：`POST /api/exchanges/mh/mh.risk/publish` |
| 临时改 TTL | 24h 延迟链路压到 15 秒实测，验完删队列恢复 |
| CDP + 无头 Chrome | 注入 Cookie、读 DOM、截图，验证真实渲染而不是“构建通过” |
| `HEX()` 解码 | 终端 GBK 显示乱码时确认库里中文是否正确（字符数 vs 字节数） |
| `docker compose config --quiet` | 部署前校验变量插值，不启动任何容器 |

### 无头 Chrome 的三个坑

1. `TaskStop` 杀不掉 Chrome 子进程，端口仍被占用 → 换端口 + 独立 `user-data-dir`。
2. `/json/list` 刚启动时可能为空 → `PUT /json/new?url` 主动创建。
3. Node 的 `fetch` 用 `127.0.0.1`，用 `localhost` 会走 IPv6 解析失败。
